### Un webhook firmado. Conserva tu auth.

- Registra una URL de webhook y un secreto compartido. Relay no reemplaza Clerk, Auth0, Supabase ni tu auth propia.
- Cada evento lleva firma HMAC, asi tu servidor aprueba, rechaza o aplaza cada registro iniciado por un agente.
- Flujos durables gestionan reintentos, verificacion por email y 2FA — sin colas ni plumbing en tu lado.

La integracion son tres campos: nombre del producto, URL del webhook y secreto compartido. Tu sigues siendo la fuente de verdad de la identidad del usuario.

<!-- content:inbox -->
### Un buzon de verificacion que el usuario realmente controla.

- Relay provisiona `<alias>@inbox.cumulush.com` por usuario — revocable en cualquier momento, con auditoria visible.
- Los agentes leen codigos de confirmacion y magic links a traves de herramientas MCP con scope, no leyendo el buzon en bruto.
- El correo entrante se retiene 90 dias con logs redactados. Usuarios y proveedores pueden revocar el alias con un clic.

Esa es la diferencia entre "pega este codigo" y "tu agente termino el onboarding" — sin darle al agente cheque en blanco sobre el buzon.

<!-- content:mcp -->
### Connection handles, no claves API en bruto.

- Los proveedores devuelven credenciales a Relay. Relay las intercambia por un `connection_id` con scope que es lo que tiene el agente.
- Los agentes llaman a las herramientas del proveedor a traves de Relay — las claves nunca se reflejan en chat, logs ni contexto del modelo.
- OAuth, claves API, service accounts y magic links son todos ciudadanos de primera. El agente nunca ve la credencial en bruto.

El agente obtiene la capacidad. El usuario y el proveedor conservan la clave. Revoca un agente sin rotar los secretos de produccion.

<!-- content:dashboards -->
### Auditar, revocar y medir a cada agente.

- `/me` — vista usuario: agentes conectados, alias activos, scopes, revocacion con un clic.
- `/dev` — vista integrador: productos, embudo de registro, rate limits por agente, auditoria, facturacion.
- Cada registro, lectura y revocacion queda logueado; hay exportaciones disponibles para cumplimiento y revision de incidentes.

Un codebase, dos personas, un rastro de auditoria. Los proveedores ven lo que hacen sus agentes. Los usuarios ven exactamente lo que sus agentes pueden tocar.

## Flujo de onboarding completo

Relay gestiona el ciclo completo sobre Vercel Workflow DevKit — resistente a fallos, reanudable e idempotente.

1. El agente llama a `POST /v1/signup` con el alias del usuario y el product ID.
2. Relay envia un webhook firmado con HMAC al proveedor. El proveedor aprueba, rechaza o pide mas datos.
3. La verificacion llega al buzon alias del usuario (`<alias>@inbox.cumulush.com`).
4. El agente completa la verificacion con una herramienta MCP con scope. Nunca lee el buzon en bruto.
5. El proveedor devuelve las credenciales a Relay. Relay las intercambia por un `connection_id` y emite `signup.completed`.
6. El agente usa ese `connection_id` para llamar a herramientas. El usuario o el proveedor pueden revocar cuando quieran.

```text
agente -> relay -> webhook del proveedor (firmado HMAC)
                \-> buzon alias con scope
                \-> bucle de verificacion (sin acceso directo al correo)
                -> el proveedor devuelve la credencial
                -> relay guarda o intercambia -> connection_id
                -> signup.completed
```

Reintentos, cancelaciones y pasos reanudables los gestiona Workflow DevKit — sin colas a medida en ningun lado.

## Modelo de confianza, en claro

La seguridad es el producto. Esto es exactamente lo que ve cada parte.

- **El agente ve:** un `connection_id` con scope, la superficie de herramientas que el proveedor expone y su propio log de auditoria. Nunca la clave API en bruto, el refresh token OAuth ni el contenido del buzon.
- **Relay almacena:** credenciales cifradas (AES-256-GCM, en capa de aplicacion) solo cuando el proveedor opta por el vault. Si no, las credenciales pasan una sola vez y no se persisten.
- **El proveedor controla:** aprobacion en cada registro, rate limits por agente, revocacion y el tipo de credencial (OAuth, API key, service account, magic link).
- **El usuario controla:** el ciclo de vida del alias, que agentes tienen una conexion y la revocacion con un clic en todos los productos.
- **Proteccion contra abuso:** webhooks firmados, puntuacion de fraude por agente, CAPTCHA bajo riesgo, reembolsos en registros fallidos y almacenamiento multi-tenant con RLS y validacion de tenant en servidor.

Si un agente se ve comprometido, el radio de impacto es el `connection_id` — no tus claves de produccion.

## SDK de 20 lineas

Pon el SDK de servidor. Relay se encarga de firmas, reintentos y la maquina de estados del flujo.

- `@relay-cumulush/server-sdk` — MIT, superficie minima.
- Verifica firmas HMAC, emite decisiones, devuelve el tipo de credencial que quieres que Relay almacene o pase una sola vez.
- Compatible con cualquier framework Node.js: Express, Fastify, Hono, handlers de Next.js.

```ts
import { relay } from '@relay-cumulush/server-sdk';

export const POST = relay.webhook({
  secret: process.env.RELAY_SECRET,
  onSignupRequested: async ({ alias, product, agent }) => {
    const user = await db.users.create({ alias, product });
    return {
      decision: 'approve',
      credential: { kind: 'api_key', value: await issueScopedKey(user.id) },
    };
  },
});
```

Relay intercambia esa clave por un `connection_id` y se lo entrega al agente. Tu conservas la clave.
